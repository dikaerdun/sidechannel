# 第 12 章　把原理落实到 FPGA 与 ASIC 的安全实现

[目录](../README.md) · [上一章](11-ml-dsa.md) · [下一章](13-evaluation.md)

以下是依据前述物理模型与掩码原则整理的工程检查方法，不是某种芯片的认证清单。

## 12.1 防护应当对应明确机制

| 防护 | 主要改变什么 | 需要注意的剩余问题 |
|---|---|---|
| 固定路径、固定访存 | 控制与地址的秘密依赖 | 数据功耗、EM、转换仍需评估 |
| 掩码 | 允许的局部变量与秘密的关系 | 高阶联合、毛刺、转换、随机数 |
| 随机延时、乱序 | 操作与观测的对应关系 | 是否可分段、对齐或横向识别 |
| 屏蔽、滤波、隔离供电 | 某些观测通道的传递函数 | 其他位置、频段与通道 |
| 平衡逻辑、预充电 | 两类数据的活动差异 | 负载、走线、毛刺与实现偏差 |
| 限制秘密使用次数 | 可累计观测的数量 | 单迹线、预训练、失败路径调用 |

没有一种措施可以不指定对手条件就称为“防侧信道”。相反，应说明它让哪条推断链更困难，增加了什么成本，保留了什么风险。

## 12.2 做一张敏感数据生命周期表

| 阶段 | 要追踪的关系 | 典型问题 |
|---|---|---|
| 输入和装载 | 明文秘密如何变成份额 | 在装载完成前是否已经泄漏？ |
| 存储 | 份额放在哪些物理资源 | 相邻周期、共享端口和旧值是否重组信息？ |
| 运算 | gadget 的输入、输出及随机量 | 非线性组合是否满足证明前提？ |
| 转换 | 算术域、布尔域、压缩、编码 | 是否短暂恢复完整敏感量？ |
| 判定 | 比较、范数、拒绝和选择 | 标志、耗时、输出选择是否泄漏？ |
| 清理和复位 | 旧状态如何消除 | 清零转换、复位后随机序列重播是否暴露关系？ |

这张表比单独统计“有多少个掩码乘法器”更接近完整模块的风险。

## 12.3 FPGA 需要特别检查什么

LUT 映射、逻辑合并、重定时、DSP 使用、BRAM 端口和布局布线都会改变物理实现。两个 RTL 模块看起来分开，综合后未必仍保留设计者假定的隔离。

保留层次或限制某些优化可能有助于维持结构，但约束本身不是安全证明。应检查综合后网表、共享资源、寄存器边界和实际数据转换。不同布局种子可能改变路径延迟、电磁空间分布和份额耦合，因此一个 bitstream 的结果不能自动覆盖所有布局。

如果使用时分复用来节省面积，务必检查前一份额留下的状态。若使用并行份额来增加吞吐，也要分析物理耦合与联合观测。串行和并行各有风险，没有只靠架构名称决定的安全高低。

## 12.4 ASIC 需要特别检查什么

RTL 功能仿真可验证算法结果，却不能完整捕获门延时、毛刺、电容和供电网络。门级时序仿真与布局后功耗分析可以提前发现部分问题；流片后仍需真实测量。

标准单元、时钟树、供电网、布线不平衡、工艺电压温度角和版图邻近关系可能改变泄漏。逻辑等价变换可以保持输出完全相同，却改变观测分布，因此 ECO 和综合优化后应重新评估受影响的安全假设。

## 12.5 建立四层证据

| 层次 | 能回答的问题 | 不能单独证明什么 |
|---|---|---|
| 算法/份额级论证 | 共享运算是否正确，局部依赖是否满足模型 | 真实模拟电路的全部行为 |
| RTL 与网表分析 | 是否有意外重组、共享或时序问题 | 完整布局和电磁响应 |
| 布局后分析 | 路径延迟、毛刺和负载的部分影响 | 实物测量链中的全部泄漏 |
| 实测与攻击验证 | 给定条件与预算下的实际可利用性 | 无限预算、所有通道下的绝对安全 |

这些证据互相补充。既不应该用形式模型忽略实测异常，也不应该用一次实验成功或失败否定所有形式推理。

## 12.6 随机数预算应当成为架构参数

若一个非线性 gadget 每次消耗 r 个随机位，每操作调用 M 次，吞吐为 F 次操作/秒，则平均随机消耗约为：

$$B_{avg}=rMF.$$

但峰值供给还取决于调度。一个流水线可能在某几个周期同时启动很多 gadget，要求的瞬时带宽高于平均值。必须设计 FIFO 深度、背压、欠供行为、复位与错误处理。

请分别报告：真实熵源需求、伪随机扩展输出需求、掩码刷新需求、跨算法域分离，以及生成器本身的保护成本。把全部数字合并成“需要多少 TRNG”会掩盖关键设计选择。

当随机量不足时，安全退化行为必须明确。例如停顿并保持安全状态，与悄悄重复使用旧随机量，是完全不同的系统语义。

## 12.7 对统一 ML-KEM/ML-DSA IP 的建议

优先统一可以给出清楚语义的模块：模加、乘公开常量、特定乘法路径、NTT 控制、受保护存储接口和随机服务。然后分别梳理两个算法的压缩、比较、采样和哈希上下文。

评价统一程度时，不能只看复用门数，还要看：跨算法是否残留秘密状态、不同模数与位宽是否改变保护前提、模式切换是否重新初始化随机域、错误退出是否清理共享资源。

研究成果最好同时给出功能正确性、保护阶数与模型、实测预算、端到端性能、随机消耗和面积。只比较未包含随机生成与转换成本的 NTT 周期数，不能说明安全解封装或安全签名的总成本。
